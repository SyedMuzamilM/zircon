# Next Git and editor interaction slices

The five user-provided Zed screenshots on November 7 establish the requested interactions more precisely than the earlier reference captures. Source attachments remain in the T3 attachment directory; this document does not claim new automated Zed interaction.

## Ordered units and acceptance

1. Finish the current Git UI correction commit: actual resize cursors, joined action/menu surfaces, per-file line-count badges, fixed branch/stash anchor and focused popover modules. Require pointer-driven placement and typing, rounded badge semantics, native NSCursor observation, and light/dark captures.
2. Build a shared diff layout model that owns file groups, collapse state, unified/split row pairing and hunk offsets. File headers show disclosure, staging state, basename/path and real addition/deletion totals. Open File is available on hover or active file and opens the correct source, with deleted/historical files handled explicitly. Expand/collapse all and previous/next hunk use the same layout model as scrolling. Test multiple files, unequal deletion/addition runs, zero-context/new/deleted/binary files and collapse/navigation behavior.
3. Add the diff toolbar below the tabs with collapse-all, unified/split, totals, hunk navigation, Stage/Unstage, Stage All and Commit. Controls must operate on the actual active file or selection, reflect busy/disabled state and remain usable at narrow widths. This is independent from choosing staged versus worktree comparison.
4. Editable uncommitted diff buffers require document-backed excerpts. Keep each source document in Workspace, map new-side excerpt byte positions to its snapshot, render deletions as immutable comparison text, and route edits through Editor.applyOutcome. Recompute comparisons from the current unsaved snapshot, reject obsolete results and preserve selections while hunks move. Unified and split views must edit the same source identity. Historical/stashed revisions remain immutable. Saving, undo, multi-cursor, UTF-8/IME, added/deleted files, external conflicts and staging after unsaved edits all require explicit acceptance. A generic text input over displayed patch text cannot pass this requirement.
5. Share a breadcrumb/action bar below normal file tabs. Show path and current symbol only when backed by real syntax/navigation data. Keep search and editor controls at the right, with split-pane-aware targets.
6. Add animated bottom extension recommendations using a notification model with stable IDs, install/progress/error/dismiss actions, persistent suppression and reduced-motion behavior. Recommendations must follow a matching available extension, without installing or opening external links automatically.
7. Replace one-process-per-highlight work with persistent parser ownership. Measure current request scheduling, process startup, source serialization, grammar initialization, parse and UI installation separately. Require latest-revision correctness, retry/cancel/shutdown isolation, bounded memory and actual edit/parse work before reporting latency. Incremental text updates and parse state follow from the persistent worker design. The grammar retry correction addresses returned failures only and makes no speed claim.

TEXT-05 recovery remains in progress in a separate storage unit. Its UI integration and forced-process-termination acceptance are still required. The original gap checklist remains open; these slices refine its Git/workspace/language/notification requirements rather than replacing them.
