# Zircon UI development roadmap

**Start with a reliable frame and a fair race.** Fix the reproduced key-sequence defect, restore the editor test baseline, and build equivalent native sidebar benchmarks for Zircon UI and GPUI. Then optimize the measured costliest phase. The first release objective is responsive, correct editing on macOS with a usable keyboard and accessibility path. The sequence below is a proposed engineering order, independent of team size or delivery dates. [Comparison and evidence](research/zircon-ui-gpui-comparison-2026-11-18.md)

## Define a win before changing the renderer

| Question | Proposed acceptance target |
|---|---|
| Is input responsive? | On a recorded reference Mac at 120 Hz, target warm input-to-submit p95 at or below 8.33 ms for wrapped typing and sidebar selection. At 60 Hz use 16.67 ms. Record missed presentations independently of CPU submission. Publish which workloads meet each target. |
| Is it faster than GPUI? | For each matched workload, call a material win at a proposed 10% lower paired p95 or better, with a 95% interval for the ratio below 1. Report ties, regressions and workloads unavailable on either side. A single list result supports a list claim only. |
| Is the optimization worth shipping? | Require equivalent visible output, focus, hit testing and text state. Investigate any repeatable p95 regression over 5% elsewhere, shifts in p99, or over 10% growth in peak memory before merging. Calibrate these provisional tolerances with repeated unchanged builds. |
| Is it better to use and maintain? | Script keyboard-only editing, IME composition, list insertion above the selection, screen-reader navigation, and cleanup after close. Require each journey to preserve the intended document, selection, scroll anchor and focus. Verify resource use plateaus over repeated open/close cycles. |

**Measurement protocol.** Pin both revisions, OS, hardware, resolution, refresh rate, fonts, scale and release settings. Use the same fixture, row content, visible state and event trace in each harness. Alternate execution order over at least ten paired fresh-process runs. Separate cold startup, warm interaction and post-edit background settling. For p99, collect at least 1,000 warm events per workload per implementation and retain per-run distributions. Use paired runs as the unit of uncertainty. Archive raw samples, runner commands, build flags, fixture hashes and correctness checks. Report input-to-submit, presentation when instrumented, per-phase CPU time, allocations, memory and frame misses. Keep results with different timing boundaries in separate columns. ## Delivery sequence

| Order | Work and ownership | Evidence required to finish |
|---|---|---|
| 1. Correctness baseline | **Framework input:** retain the actual pending sequence or matching candidate set. **Editor:** fix atomic replacement options, formatting/import checks and completion continuity. Separate the displayed completion revision from the request in flight. | With only `g f` and `x l` bound, `g l` invokes neither. Both valid sequences still work after a context switch or failed prefix. During a delayed LSP response, extending an identifier preserves the list and Enter cannot apply stale edit ranges. Run full Linux checks and repeat persistence on macOS. |
| 2. Instrument a real frame | **Framework runtime and benchmark harness:** count views constructed, nodes measured/arranged, rows painted, text bytes shaped, scene elements emitted/replayed, and cache bytes/evictions. Attribute elapsed time to input, tree construction, layout, paint and submission. | One command per framework replays the same sidebar trace. A warm row update and a forced full rebuild produce equivalent visible rows and hit targets. Publish an unchanged-build noise baseline. Check instrumentation overhead with counters disabled. |
| 3. Reduce unnecessary view construction | **Framework runtime:** if phase 2 shows construction dominates, prototype opt-in cached views on the project sidebar. Track the dependencies actually read. Include bounds, font generation, inherited style, focus, hover and input routing in invalidation. Keep an uncached reference path. | Changing one row avoids constructing eligible unaffected views. Compare full and cached paths through scroll, resize, theme/font changes, focus, failed allocation and eviction. Preserve committed-frame rollback and cache bounds. Land only after the paired comparison justifies the extra state. |
| 4. Scale text and diagnostics | **Editor model:** share revisioned diagnostics and query intersections for the visible range. **Framework graphics:** profile a dedicated wavy-underline command. **Text:** profile wrap-index maintenance and shaping after a middle-of-buffer edit. Ship these as separate changes. | With a fixed viewport, raise offscreen diagnostics from 100 to 10,000 and show that visited marks track intersecting ranges. Validate zero-width, end-of-line, wrapped and overlapping issues. Compare old/new wave output at 1× and 2×. Record unchanged-line reshaping, input p95 and peak memory before and after each change. |
| 5. Make custom UI accessible and text input dependable | **Framework platform and controls:** design stable semantic IDs, roles, labels, values, bounds, focus and actions for the committed frame. Deliver a macOS accessibility bridge. Add grapheme, mixed-direction, marked-text and reduced-motion journeys. Start the semantic identity design alongside phase 2. | VoiceOver can navigate a virtualized list, identify the selected completion, read a diagnostic and activate a control. A cached frame, row splice and focus transfer preserve identity. CJK IME composition commits once in the correct document. Combining marks and emoji sequences survive navigation and deletion. |
| 6. Broaden the toolkit around a second consumer | **Controls and platform:** use a small standalone app to exercise list splices, scroll-to-reveal, popup placement, async image loading and error handling. Select a second desktop backend according to product demand. Linux is a practical first candidate given existing headless CI. | A developer can build the sample from the public API and diagnose a slow frame. On the selected OS, exercise native window creation, font fallback, clipboard, IME, pointer/keyboard input, accessibility and GPU presentation. Run the same journeys on macOS to catch portability regressions. |

If phase 2 instead identifies text shaping, queue stalls or GPU time as dominant, advance that item ahead of view caching. Ownership-safe caching, accessible semantics and correct input remain acceptance conditions for whichever path ships.

## Benchmark backlog

| Fixture | What to vary | What would make the result convincing |
|---|---|---|
| Project sidebar | Fixed and variable heights, one million logical rows, 200 deterministic positions, one changed selection, insertion above viewport | Match row text, overscan and viewport on both sides. Verify first/last visible row, focus and scroll anchor. Measure scroll and one-row updates separately. |
| Editor-like text surface | 32 KiB and 1 MiB, wrapping on/off, font fallback, cold/warm caches, middle insert/delete/undo | In the toolkit harness use the same text and decorations. In the real editor additionally verify document bytes, caret and service readiness. Report those two test levels independently. |
| Dense diagnostic viewport | Fixed on-screen errors with increasing offscreen counts, long underlines, split panes and repeated hover | Distinguish document query time, scene construction and GPU time. Verify severity, position, hover message and refresh when an issue changes at the same revision. |
| Idle and animation | Idle window, cursor blink, hover-only update, retained SVG transform, reduced motion | Count wakeups, rebuilt views and frames presented. Verify that the idle window settles and that compositor-only animation avoids full layout. |
| Long session | Open/close many views, change fonts, scroll new content through the caches, cancel work when closing windows | Record live allocations, cache high-water marks, queue depth, canceled-job delivery and post-close memory trends. Keep traces for the worst frame. |

## First three pull requests

1. **Fix sequence matching and add the mixed-prefix regression.** This is small, reproducible on Linux, and protects command correctness in every consumer.
2. **Restore the Linux baseline.** Repair atomic recent-project/settings writes and run save/reopen tests on both first creation and replacement. Clear the formatting and import-order failures, then record the complete suite result.
3. **Add paired sidebar drivers and phase counters.** Start with one changing selection in a fixed viewport. Publish the two traces and the first bottleneck before opening a renderer rewrite. The completion continuity regression can proceed independently in the editor.

The first milestone review should be able to show one correct keyboard sequence, one green full-suite run, and two comparable native frame traces. Those results decide the first performance change.
