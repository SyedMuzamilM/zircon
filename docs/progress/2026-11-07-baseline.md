## Input-routing investigation

The historical standalone `TextDispatchFailed` did not recur in the initial fresh suite or ten repeated focused runs today. All ten recorded foreground queue delivery. That observation alone was not treated as a fix.

A two-window experiment then tested the old assumption that a queued key remains bound to the event's `windowNumber`. It posted `x` naming window A, made B the key window before pumping, and asserted delivery to A. The test failed with:

```text
routing counts: first keys=0 text=0; second keys=1 text=1
expected 1, found 0
```

This establishes focus-sensitive redirection of the synthetic event, not a production AppKit bug. The historical failure did not retain enough counters to prove its exact circumstances. The demonstrated unsafe test assumption is removed:

- The surface test finds its own window by title and sends the key through that window's real first responder. Pointer queue, resize, rendering and close checks remain.
- A regression switches focus between two windows and verifies window-bound key/text delivery stays on the intended window.
- A separate foreground queue check verifies delivery follows the current key window. It explicitly skips when activation is unavailable.
- All routes retain exact key/text counts. Failure output includes activation, target-key and first-responder state.

Production keyboard interpretation and native text callbacks are unchanged. This closes the native-test routing correction in TEXT-01. It does not establish full IME, dead-key, terminal Unicode or accessibility acceptance; those remain TEXT-02 and related tasks.
