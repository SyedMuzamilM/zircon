## Main findings for the parent

1. The useful comparison is the complete edit transaction. Zed shares live source buffers across file editors, project-search results, references, diagnostics, and working diffs. Selection, undo, save, LSP ranges, and source navigation have to preserve identity across those views. A panel that displays matches alone does not establish this workflow. [D: multibuffers][multi-doc], [S: projected edits][multi-edit], [S: grouped transactions][multi-history].
2. Keep disk, buffer, index, and HEAD separate in the audit. Current Zed can display dirty-buffer changes in live diffs. Both whole-file stage/unstage and editor hunk stage/unstage paths can save corresponding dirty buffers first. This is a concrete product policy to compare, not a reason to assume either save policy is universally preferable. [S: whole-file saves][git-save], [S: whole-file stage][git-stage], [S: hunk saves][hunk-save], [S: hunk stage][hunk-stage].
3. Global project search uses in-memory text for indexed open files and buffer snapshots for match ranges. It is not equivalent to invoking a disk-only grep. It also has ignore rules, explicit exclusions, deferred indexing and bounded result delivery. [S: open buffers][search-open], [S: candidate contents][search-candidate], [S: result bounds][search-bounds], [D: deferred indexing][scan-doc].
4. LSP support is conditional on adapters, server capabilities and configuration. The client implements semantic workflows and lifecycle management; that does not prove every server, every language or every stale-response race works. In particular, current LSP initialization advertises UTF-16, and incremental updates use UTF-16 ranges. Do not describe this as verified support for arbitrary negotiated position encodings. [S: capabilities][lsp-init], [S: change notifications][lsp-change].
5. Broad claims such as "every diff is editable", "committing always stages all tracked files", "all project files are always searchable", and "Git changes refresh instantly" need narrowing. The evidence and corrections are recorded below.

### Important Git wording corrections

- "All diff views are editable" is too broad. Working Project Diff and Unstaged Diff construct writable multibuffers; Staged Diff explicitly uses `Capability::ReadOnly`; CommitView does too. File-history commit diffs and stash diffs use CommitView. The Git docs' shared wording about Project Diff, File History and Stash Diff should not override these source facts. [S: staged][staged], [S: commit/file history][commit-open], [S: read-only commit][commit-readonly], [S: stash opening][stash-open], [S: stash actions][stash-view].
- "Commit automatically stages all tracked files" omits the existing-index branch. With staged changes present, source commits the staged state; implicit tracked-file staging happens in the alternate branch. [S: `commit_changes`][git-commit].
- "File staging uses only saved bytes" misses Zed's pre-save step. Both whole-file and hunk workflows can save dirty buffers. The parent should compare this policy explicitly with Zircon rather than assuming one editor's policy. [S: file][git-stage], [S: hunk][hunk-save].
- Hunk actions operate on resolved diff hunks intersecting selected ranges. Do not credit arbitrary selected-line staging until its actual semantics are verified. [S: selected hunk resolution][hunk-stage], [S: index mapping][git-hunks].

## Most valuable comparison scenarios

These are proposed parent-audit criteria, ordered by likely user impact and information gained. They do not assign a pass/fail to Zircon.

1. **One change through every view.** Open two files, search a shared token, edit one result, observe both source tabs and working diff, undo from the results editor, redo, save and inspect disk. Repeat with one operation spanning both files. This probes identity, excerpt mapping, grouped history and save ownership together.
2. **Partial staging with unsaved work.** Create two hunks, stage one, edit both again without saving, inspect staged/unstaged/combined diffs, stage one hunk and commit. Record buffer, disk, index and HEAD after each action. Repeat unstage and discard from each grouping. This distinguishes real index semantics from visual checkbox state.
3. **Search coverage and replacement.** Mix ordinary/ignored/excluded/deep files, a dirty open file, UTF-16 text, a binary file and an untitled buffer. Search literal, Unicode insensitive, whole-word, multiline and regex patterns; apply path filters, replacement captures and undo. Cross the result threshold and inspect the truncation signal before Replace All.
4. **Cross-file language edits under load.** With the same server/version, completion auto-import, signature help, hover, definition/reference and rename over dirty/open/closed files. Insert emoji before target ranges. Restart the server while work is pending and verify session cleanup. Compare actual outputs and stale-result handling, not only command availability.
5. **Save conflict and encoding integrity.** No-edit round trip for LF/CRLF, BOM, UTF-16 and a legacy encoding; unsupported character insertion; external writes to clean and dirty buffers; all conflict-prompt paths. Inspect bytes and failure handling.
6. **History and recovery.** Open a file at a commit, try editing protected historical text, return to the working file, resolve a Git conflict, stash a partially staged file, apply/pop with a conflict, and switch branch/worktree with dirty buffers. Observe what remains recoverable and where continuation requires the terminal.
7. **Syntax and display correctness.** Nested/injected languages, malformed input, fold edits, rectangular selections with tabs/wrap/Unicode, multiline regex and undo. Keep syntax highlighting, semantic tokens, fold source and symbol source settings explicit.

The matrix uses operation correctness and recovery as comparison criteria. No score, feature-count ranking, chart, benchmark or Zircon defect claim is inferred from this research.
